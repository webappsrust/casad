## Project description

Casad is an open-source, self-hosted replacement for the organization's identity, directory, DNS, email, collaboration, and core IT infrastructure stack. It brings together the capabilities organizations otherwise assemble from FreeIPA, LDAP services, Windows Server and Active Directory Domain Services, Windows DNS, Zitadel, Zentyal, OpenGroupware, Microsoft Exchange and Microsoft 365/Outlook, and Google Workspace. Casad targets 1:1-or-better functional parity with Windows AD/DC, Linux SSSD-based domain integration, and equivalent macOS directory and single-sign-on integration. The server targets Linux and BSD hosts; the companion CLI and agent follow AI.md's supported cross-platform targets. Clients authenticate through their native platform capabilities. Administrators manage the complete service stack through the web admin UI, and users access their services through a web portal.

## Business logic

### Product scope & non-goals

- Provide a Linux- and BSD-hosted domain and full infrastructure stack, including its installation and lifecycle management.
- Provide a complete web administration control plane for domain setup, routine administration, diagnostics, security, recovery, and every supported infrastructure service. The admin UI must provide 1:1-or-better management coverage for the complete Casad-supported Windows Server/AD-compatible replacement scope: every supported service role, policy, listener, identity object, network service, integration, and recovery operation must be discoverable and configurable there. No supported product capability may be CLI-only or TUI-only. The UI must manage real service capabilities rather than serve only as a status dashboard.
- Provide deployment readiness and lifecycle workflows through the admin UI: assess host and service-role compatibility, network/port conflicts, resource capacity, and required dependencies before installation or migration; show installation, upgrade, service health, and recovery status; require explicit administrator confirmation before destructive migration or data replacement.
- Provide a web user portal and integrated application suite for identity/account self-service, webmail, calendars, contacts, tasks, files, sync and sharing, photos/media, activity and notifications, dashboards/search, notes, bookmarks, RSS/news, forms/surveys, collaborative spaces/wiki, project boards, chat/video meetings, collaborative office documents, and service discovery. The authoritative domain identity governs account identity and group membership; federation supports web sign-in without creating a separate domain-password authority. Public self-registration and generic application organizations are out of scope; a domain is the organizational boundary. User profiles and assigned-device data are visible only to the user and authorized administrators. Provide the user-facing capabilities represented by the supported Nextcloud and OpenCloud first-party/featured app catalog, including app-specific access, sharing, workflow, storage, and collaboration functions where defined in Casad's compatibility catalog. Offer interoperable client access where relevant standards support it. Administrators can discover, enable, disable, configure, update, scope, and monitor every supported app and integration from the admin UI; users launch and manage permitted services from the portal. Maintain a versioned app-by-app compatibility catalog and do not imply that every third-party extension or undocumented proprietary feature works automatically.
- The Windows Server replacement scope covers the complete organization-infrastructure role catalog, not only AD DS: directory services (AD DS/AD LDS equivalents), certificate services, federation and identity services, DNS, DHCP, IPAM, RADIUS/network policy, file and storage services (SMB, DFS namespaces/replication, quotas, deduplication, NFS, iSCSI, work-folder synchronization and storage migration), print/document services, web hosting/reverse proxy, remote access/routing/VPN, remote application/desktop services, virtualization/VM lifecycle, failover and cluster services, update management, backup/recovery, deployment/provisioning, activation/license services, and supported legacy interoperability services. Each capability is part of the browser-administered role catalog and requires an explicit compatibility-matrix result for BSD/Linux, clients, dependencies, lifecycle, migration, recovery, and validation. Casad provides a Linux/BSD-native functional equivalent for every in-scope Windows Server role; it does not claim to reproduce Windows kernel-specific behavior or proprietary protocols. Any role without a validated equivalent is an unresolved product gap, blocks a complete parity claim, and must be shown with its impact and alternative in the admin UI.
- Replace the need to assemble separate directory, identity provider, DNS, email, collaboration, and productivity systems. Product capability parity covers the relevant identity and directory functions of FreeIPA, LDAP, Windows Server AD/DC, and Zitadel; Windows DNS; groupware capabilities of OpenGroupware; and hosted mail, calendar, collaboration, and productivity services comparable to Microsoft Exchange, Microsoft 365/Outlook, and Google Workspace. This is a product capability goal, not a claim of compatibility with proprietary internals or undocumented protocols.
- Maintain an authoritative domain directory for identities, groups, computers, policies, internal DNS, and secure dynamic DNS. Provide standards-based OIDC/OAuth 2.0 and SAML 2.0 web identity-provider and relying-party/federation capabilities, with discovery, metadata, signing-key rotation, client/provider lifecycle, consent and claim/group mapping, logout, session revocation, and audit. Support multiple configured providers and protocol profiles; compatibility is measured against published standards and a verified interoperability matrix. External identity federation must not replace or corrupt authoritative domain identities, and web federation must not be represented as LDAP/Kerberos domain authentication.
- Target 1:1-or-better functional parity for Windows AD/DC domain workflows and clients, Linux domain integration through SSSD and other established client stacks, and equivalent macOS directory, Kerberos, and SSO workflows. Support Linux and BSD native clients, Windows 7 and later Professional, Enterprise, and Ultimate clients, Windows Server 2012 and later as domain member servers, and supported macOS clients. Domain logins use the native platform authentication flow: SSSD/PAM/NSS on supported Linux systems, supported native directory/PAM/NSS mechanisms on BSD, native directory and SSO mechanisms on macOS, and Windows domain authentication on Windows. The Casad CLI and telemetry agent are not authentication providers and do not perform domain login. Do not require Windows Server as a domain controller. Target a fresh-domain baseline equivalent to Windows Server 2012 R2. Validate and publish an interoperability matrix; do not claim unverified compatibility or reproduce claims about proprietary internals.
- Linux SSSD parity includes DNS-based discovery, NSS/PAM identity and authentication, Kerberos, group/access policy, credential caching for supported offline login, and service authorization. macOS parity covers Apple's native AD directory binding path and its Kerberos/enterprise SSO path as separate integrations. Casad's CLI and agent do not replace native macOS login or Apple's Platform SSO extension. See [Red Hat SSSD and AD integration](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/integrating_rhel_systems_directly_with_windows_active_directory/) and Apple's [Active Directory integration](https://support.apple.com/guide/deployment/integrate-mac-computers-with-active-directory-depd1a7cad1f/web), [Directory Utility](https://support.apple.com/guide/directory-utility/diru39a25fa2/mac), and [Platform SSO](https://developer.apple.com/documentation/authenticationservices/platform-single-sign-on-sso).
- Provide Windows AD/DC-compatible directory and domain workflows covering users, groups, computers, organizational units, delegation, access policies, Kerberos, secure LDAP, DNS discovery and dynamic updates, policy distribution, trusts, replication and recovery, time synchronization, domain join, secure channels, and machine-account lifecycle. Claim compatibility only for validated client and server combinations; do not imply compatibility with proprietary internals.
- Support native centralized account login on BSD and Linux, with 1:1-or-better functional parity for Linux SSSD-based domain integration. Support domain discovery and join, identity and group lookup, Kerberos authentication, password changes, access policy, client-supported offline login, and SMB access through each OS's native authentication stack. Describe policy support only to the extent each client platform implements it; do not claim full Windows Group Policy processing on BSD or Linux. The CLI and agent do not authenticate interactive domain users.
- Support equivalent macOS directory integration and SSO workflows, including centralized identity and group resolution, Kerberos authentication, password policy and changes, and supported file-service access. Treat native directory binding and Apple's Kerberos SSO extension as distinct supported integration paths where applicable. The Casad server remains Linux/BSD-only; its CLI and agent follow AI.md's cross-platform targets.
- Provide browser-based Group Policy authoring, including ADMX/ADML, Registry.pol, Group Policy Preferences, and baseline policies, without requiring RSAT or GPMC. Permit normal logon and startup policy scripts; do not provide a remote WinRM/PowerShell command runner.
- Windows policy compatibility includes directory-based Group Policy containers, SYSVOL policy content, supported client-side extension formats, policy links and scope, and Group Policy Preferences. Browser authoring is Casad's management interface; compatibility is verified against real Windows clients and is not inferred from file-format support alone. See [Microsoft Group Policy overview](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-policy/group-policy-overview), [Group Policy Preferences](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-policy/group-policy-preferences), and [ADMX Central Store guidance](https://learn.microsoft.com/en-us/troubleshoot/windows-client/group-policy/create-and-manage-central-store).
- Provide interoperable Kerberos domain services for supported BSD and Linux clients and services, including realm and KDC discovery, principal and service-principal lifecycle, pre-authentication, ticket issue and validation, renewal and revocation policy, key versioning and rotation, modern encryption, authorization-data interoperability, delegation and trust behavior, clock-skew policy, password changes, auditing, and service-key lifecycle. Legacy compatibility must be explicit and must not make deprecated cryptography the default.
- Provide split public and internal DNS for the same registered domain. Public DNS is authoritative for public records; internal DNS serves the private domain zone and secure dynamic updates. The management interface supports approved public mail records in both views. Never expose internal directory or Kerberos services globally. Internal DNS may be made available over VPN.
- Include mail and groupware services for users: inbound/outbound SMTP, authenticated submission, IMAP, POP3, webmail, user mail rules, mailbox quotas/delegation, calendaring, contacts, tasks, and scheduling. Support spam, phishing, and malware controls; SPF, DKIM, DMARC, MTA-STS, TLS reporting, and applicable DNSSEC/DANE policy; quarantine, abuse reporting, retention, and mailbox migration. Preserve existing mailbox data during configuration regeneration and migration. The service must meet the product replacement goal for hosted mail and groupware without requiring Exchange, Microsoft 365/Outlook, or Google Workspace.
- Provide managed IPv4 and IPv6 DHCP scopes, reservations, leases, failover, and secure DNS registration, plus NTP service for domain time synchronization. Provide central SMB file shares with domain-based authorization and user-portal access. These are managed from the web admin UI and exposed only on configured trusted networks.
- Provide network print services for supported Windows, Linux, BSD, and macOS clients, including managed queues, access policy, approved driver packages, job status, and user printer discovery/submission. The admin UI manages queues, drivers, policy, and service health; user access follows domain permissions. Never distribute an untrusted driver package as an administrative convenience.
- Include certificate services and enrollment compatible with ACME, SCEP, and Windows domain certificate auto-enrollment for supported clients. Integrate with administrator-selected RFC 7030 EST certificate authorities at their own standards-compliant origin and manage their trust, enrollment policy, health, and client configuration in the admin UI.
- Provide VPN interoperability for OpenVPN, WireGuard, and IPsec clients, including user self-service profile issuance and revocation. Administrators manage VPN policy through Casad.
- Provide a Casad-owned cross-platform agent that reports supported device inventory, host health, metrics, and security events to the Casad server. Its reports may include OS and package state, local users and groups, services, certificate metadata, and firewall posture, but never credentials, private keys, or file contents. Agent reporting does not provide domain authentication or host administration.
- Agent reports cover stable device identity, host and OS details, resource summary, installed applications/packages, local users and groups, service/update state, certificate metadata, firewall posture, health, and last contact. Reports are bounded, tracked for freshness, and visible only to Server Admins, authorized domain administrators, and users assigned to the device. Agent reporting does not grant host administration, domain identity authority, or access to other devices.
- Provide a scoped managed-device view for authorized administrators and read-only views for users assigned to those devices. Users cannot issue host-management actions unless they separately hold an explicit delegated permission. A device's reported capabilities and health do not grant authority over its domain identity, other devices, or the Casad server.
- Provide optional integration with third-party mobile-device management for Apple mobile devices and Android Enterprise. Casad does not ship mobile apps or agents; enrollment and mobile policy remain controlled by the configured MDM provider. MDM integration depends on administrator-configured Apple and Google platform services; provider, authorization, or push-service outages can delay or prevent mobile enrollment and policy delivery but do not change Casad domain identity or access policy.
- Windows domain clients use native domain authentication; Casad's Windows CLI and agent provide administration and telemetry without acting as authentication providers. The configured MDM provider remains responsible for mobile enrollment and policy delivery.
- Provide first-party unified XDR/SIEM and host observability across supported agent platforms. Wazuh and Beszel are capability research references only, not Casad runtime components. Support standard syslog and documented API/webhook connectors for third-party firewalls, DNS, mail, identity, VPN, network sensors, and security products. Provide CPU/load, memory/swap, filesystem/inode, disk I/O, network, service, and health history, with temperature, SMART, ZFS, container, process, and virtualization metrics where supported. Include alert and incident workflows with scoped, auditable response approvals.
- Target Linux server releases including Fedora, RHEL/Alma/Rocky Linux 9 and 10, Debian 13, and Ubuntu 24.04 and 26.04 LTS. BSD server support is limited to releases recorded in the verified compatibility matrix.
- The Casad server receives reports from its cross-platform agent. Server-side monitoring covers supported BSD/Linux servers, while endpoint telemetry covers each supported agent platform recorded in the compatibility matrix.
- Support single-host and multi-host deployments. For a single host expected to exceed 500 users or 1,000 devices, alert administrators to capacity requirements before deployment. Multi-host deployments must preserve service availability and data through placement, replication, and recovery.
- Provide two-host full-stack availability as an option. Protect acknowledged writes and prevent split-brain; do not promote a peer when safe write ownership is uncertain. Automatic failover requires an outage exceeding five minutes and verified quorum plus fencing or witness evidence. Automatic failback requires the original host to be healthy and synchronized for 60 minutes. Preserve and recover each service's data according to its consistency and availability requirements.
- Support storage of application files and backups. Preserve the integrity, permissions, and recovery of domain policy data on every supported platform. Encrypted remote backups run nightly and before changes, retain 30 daily and 12 monthly copies by default, and support restore checks.
- Public service exposure is configurable per deployment, including split internal/external exposure and one-edge or dual-edge layouts. Apply service-specific abuse limits and bans first; use global bans only for high-confidence cross-service abuse.
- Project code is MIT licensed. All product capabilities ship without licensing restrictions or paid feature gates.

### Network ports & protocol exposure

All HTTP pages and JSON APIs share the AI.md HTTP listener and reverse-proxy model; feature pages do not get separate HTTP ports. The app binds to container TCP 80 by default. Production ingress uses the reverse proxy on TCP 80/443; TCP 80 may redirect to HTTPS or serve ACME HTTP validation. Direct local development or bare-host HTTP listeners follow AI.md's `64xxx` port convention; that is not a raw protocol port and must not replace standard public HTTP/HTTPS ingress where ACME or user access requires it. Raw protocol listeners use their standard ports, never HTTP proxying or random host-port remapping. Administrators can expose service groups independently; directory, file, and management protocols are restricted to trusted LAN/VPN interfaces. The external firewall must allow only protocols enabled for that deployment.

### Roles & permissions

- Host administrators control operating-system privileges and are separate from domain administrators. Casad must never store the host root password.
- Casad platform administrators manage the service stack, infrastructure policy, integrations, and recovery.
- Domain administrators manage domain-wide identities, computers, DNS, and policies.
- Delegated administrators and helpdesk users receive only the domain, service, or endpoint-management permissions assigned to them.
- Helpdesk operators may perform only explicitly delegated user and computer support tasks. Auditors may review configuration, security events, and administrative activity without changing protected state. Service identities have only the privileges required by their workloads.
- Domain users authenticate against the authoritative domain identity and use services according to their assigned groups and policies.
- Domain-user web access is bound to a stable identifier from the authoritative domain directory. Account disablement or removal and group/delegation changes must take effect in Casad access decisions without relying on stale cached authorization. Domain-user authentication supports the configured MFA, passkey, and account-recovery workflows while preserving the directory as the password and group authority.
- A domain administrator's authority applies only to explicitly assigned domains and objects. Casad server administration does not grant domain administration or host-root authority by default; domain administration does not grant Casad platform or host authority.
- External identity providers may authenticate users through configured federation; the domain directory remains authoritative for domain identity.

### Data model & sensitivity

- Domain identities, group memberships, computer accounts, DNS records, and Group Policy content are security-sensitive administrative data.
- Passwords, tokens, private keys, certificates, VPN profiles, federation credentials, and backup encryption material are secrets and must not be exposed through logs or ordinary exports.
- Mailboxes, mail metadata, endpoint inventory, security events, and audit history contain private or operationally sensitive information.
- Managed-device assignments, agent capabilities, mobile enrollment state, and third-party MDM connection metadata are sensitive operational data; provider credentials and enrollment secrets are secrets.
- Configuration, service state, and backups must be attributable to an administrator and recoverable without exposing their secrets.

### Trust boundaries & external services

- The public Internet and public DNS are untrusted. Publicly exposed services must not grant access to internal AD protocols.
- The domain directory is authoritative for domain identity and internal DNS. Identity-federation providers are authentication boundaries, not replacements for domain identity.
- External OIDC/SAML providers are trusted only for the claims and authentication flows explicitly configured by an administrator; provider outages must not corrupt domain identities.
- Public DNS, certificate authorities (including externally hosted RFC 7030 EST authorities), VPN peers, remote backup destinations, vulnerability/advisory data feeds, and explicitly configured third-party telemetry sources are external dependencies with explicit availability and trust limits. Casad's monitoring/observability pipeline and agents are first-party components. Feed outage makes vulnerability findings stale and must be visible; it does not stop local event collection, metrics, or detections. External EST outage prevents enrollment or renewal through that authority; it does not block Casad-hosted ACME, SCEP, or WCCE enrollment.
- Optional mobile-device management integrations receive only the device and policy data required for their configured functions. Their vendor APIs and Apple/Google enrollment services are separate trust boundaries; failures limit mobile enrollment or policy synchronization and do not disable the domain directory or core Casad services.

### Threat model & abuse cases

- Protect domain credentials, administrator access, signing keys, certificates, mail, backups, and Group Policy from theft, tampering, and unauthorized disclosure.
- Protect Kerberos keys and tickets, directory integrity, BSD/Linux native client login availability, and private files and mail. Defend against Kerberos replay, forgery, downgrade and ticket abuse; unauthorized directory access or modification; SMB relay; DNS/DHCP spoofing; and abuse of legacy client compatibility.
- Defend against credential stuffing, compromised federation providers, privilege escalation, malicious administrators, and unauthorized group or policy changes with least privilege, strong authentication, and attributable audit records.
- Treat DNS changes, public mail records, Group Policy content, endpoint reports, federation metadata, and uploaded configuration as potentially malicious inputs. Prevent unauthorized public-record changes, DNS abuse, and malicious policy execution.
- Prevent public attackers from reaching internal SMB, LDAP, Kerberos, or management interfaces. Rate-limit exposed services and use bans scoped to the affected service unless cross-service abuse is high confidence.
- Defend mail users and public mail services against spam, malware, phishing, account abuse, and resource exhaustion.
- Protect agent reporting and backup paths from data exfiltration, replay, and unauthorized restoration. Agent report endpoints accept device data only; do not provide server-issued remote tasks, unrestricted shell access, or a WinRM/PowerShell runner.
- Preserve acknowledged service data during failover and prevent split-brain writes. If quorum or fencing cannot establish safe ownership, fail closed and require recovery.

### Security decisions & exceptions

- The public registered domain and AD DNS domain are the same domain, so internal and public DNS views must remain separated and carefully controlled. The Windows Server feature comparison is role- and version-specific; a parity claim requires validated Casad service and client behavior for each listed capability, not a matching label in the admin UI.
- Webmail is a domain-user service, distinct in purpose and access from administrator mail configuration.
- The domain directory remains authoritative for domain identity when external identity providers are used.
- Host-level administration and domain administration are distinct security roles. Casad does not retain the host root password.
- Public exposure is configurable, but internal AD protocols are never globally exposed.
- Group Policy may provide Windows domain interoperability through standard policy mechanisms; arbitrary remote command execution is out of scope.
- Automatic failover is allowed only with verified quorum and fencing or witness evidence. Uncertain write ownership must stop promotion.
- Mobile apps and mobile agents are out of scope.

Native mail access supports SMTP relay and submission, IMAP, optional POP3, and ManageSieve on the ports above. Mail services publish applicable DNS SRV records for submission, IMAP/POP3, CalDAV (`_caldavs._tcp`), and CardDAV (`_carddavs._tcp`), with service paths in TXT records where required, so compatible clients can discover endpoints. Voice/video media uses the optional STUN/TURN listeners and bounded media UDP range in the port table only when a supported meeting service is enabled. Public web federation uses the AI.md-defined authentication routes. Casad identity-provider interoperability also exposes the OAuth/OIDC, SAML, LDAP, and discovery protocol endpoints below. DNS, Kerberos, LDAP, SMB, DHCP, NTP, VPN, CalDAV/CardDAV/WebDAV, and directory replication are native protocol interfaces rather than JSON routes. ACME paths follow [RFC 8555](https://www.rfc-editor.org/rfc/rfc8555.html); SCEP query and PKIOperation behavior follows [RFC 8894](https://www.rfc-editor.org/rfc/rfc8894.html); EST is provided through configured external RFC 7030 authorities at their own origin. Mail discovery follows [RFC 6186](https://www.rfc-editor.org/rfc/rfc6186.html) and calendar/address-book discovery follows [RFC 6764](https://www.rfc-editor.org/rfc/rfc6764.html).
