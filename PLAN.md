# Casad Implementation Plan

Human-owned implementation plan. Follow AI.md as the default HOW specification, SPEC.md for the BSD/Linux server and artifact boundary, and IDEA.md for product requirements. Preserve this plan's structure; mark individual tasks complete only after implementation and verification.

## 1. Project Rules and Platform Boundary

- [ ] Read relevant AI.md sections before each workstream: Parts 5/10/11 for configuration, database, and security; Part 14 for API; Part 16 for frontend/accessibility; Part 17 for Server Admin UI/auth; Part 33 for CLI/agent; Part 34 as activated in SPEC.md and constrained by IDEA.md domain-identity requirements. Read the relevant service-specific sections before each integration; follow only the project overrides recorded in SPEC.md and the product acceptance in IDEA.md.
- [ ] Keep the Casad server binary and server releases limited to Linux and BSD; support Linux architectures and BSD releases only where recorded in the verified compatibility matrix.
- [ ] Build the companion CLI for all AI.md Part 33-supported targets, including supported Linux, BSD, macOS, and Windows targets, with platform-specific packaging validated independently from server support.
- [ ] Implement the Casad runtime agent for all AI.md Part 33-supported targets, using its naming, service, registration, update, security-telemetry, and observability rules. Build and validate OS-specific collectors independently; Casad server support remains limited to BSD and Linux.
- [ ] Implement the AI.md Part 34 user portal only for the domain-user product scope in IDEA.md: the authoritative domain directory remains the identity and password authority, and public self-registration is disabled. Do not implement generic Part 35 application organizations.
- [ ] Keep contributor subagents under `.claude/agents/` distinct from the Casad runtime agent; contributor-tool support does not imply Casad binaries for those platforms.
- [ ] Preserve AI.md as the binding implementation specification; apply only the user-requested Part 33 addition for first-party security telemetry and host observability, with product intent in IDEA.md and the BSD/Linux artifact boundary in SPEC.md.

- [ ] Implement first-run setup, interactive and unattended install, configuration validation, privilege handling, structured status/health, service-manager integration, and safe updates.
- [ ] Support current Fedora, RHEL/Alma/Rocky 9 and 10, Debian 13, and Ubuntu 24.04 and 26.04 LTS.
- [ ] Support BSD server releases only as they are recorded in IDEA.md's verified compatibility matrix; document each supported release's package source, service manager, filesystem/service capabilities, and unsupported roles before claiming support.
- [ ] Create a verified distribution compatibility matrix for package names, repositories, service units, service capabilities, and unsupported features. Use disposable Docker environments for package discovery, then verify host-specific behavior with supported physical systems.
- [ ] Produce a versioned package map for every supported server release: current Fedora stable at each Casad release, RHEL/Alma/Rocky 9 and 10, Debian 13, Ubuntu 24.04 and 26.04 LTS. For each component, record the exact package name(s), repository/source, minimum supported version, install/upgrade/remove method, service unit, config/data paths, required capabilities, and whether it is native, containerized, downloaded, or unsupported.
- [ ] Cover package-map rows for OS prerequisites and firewall tooling; Samba AD DC and client/admin tools; BIND; Keycloak and its container runtime; Casad's AI.md-default embedded SQLite for single-host installs and PostgreSQL for multi-host deployments; PostgreSQL for Keycloak persistence; Postfix, Dovecot, SpamAssassin, ClamAV, DKIM/DMARC, Sieve, and Roundcube runtime; ACME/SCEP/WCCE and CA candidates; external RFC 7030 EST authority integrations; OpenVPN, WireGuard, strongSwan; SeaweedFS; backup tooling; and Casad-owned security telemetry and observability components. - [ ] Keep package mappings data-driven and keyed by exact distribution ID, major version, architecture, and component. Add package-map validation for missing, duplicate, stale, or unsupported entries; installation must fail with an actionable compatibility error before changing the host when a required component has no valid mapping.
- [ ] Record repository enablement, signing-key provenance, package signature verification, pinning/update policy, and rollback behavior for every non-base repository or externally downloaded artifact. Never execute an unverified download as root.
- [ ] Preflight CPU, memory, storage, networking, and required ports against deployments targeting more than 500 users and 1,000 devices; report limits rather than promise unsupported capacity.
- [ ] Make the platform preflight report exact detected OS/version/architecture, resolved package-map entries, missing repositories/packages, port conflicts, storage estimates, and unsupported requested roles before installation; require explicit confirmation before any irreversible service migration or data replacement.

## 3. Domain, Identity, DNS, and Policy

- [ ] Integrate Samba AD DC as the authoritative domain identity and internal DNS service, including secure dynamic updates, domain join, groups, computers, and SYSVOL.
- [ ] Integrate Keycloak for web SSO, Samba-backed identity federation, and external OIDC/SAML providers. Run Keycloak using its official container distribution; persist and back up its database and configuration.
- [ ] Enforce the naming relationship: AD DNS domain is the domain FQDN, Kerberos realm is the uppercase realm, and the corresponding Keycloak organization matches that realm.
- [ ] Implement split public/internal DNS for the same registered domain: Samba for internal AD DNS, BIND for public authoritative DNS, with controlled public mail-record management in both views.
- [ ] Keep SMB, LDAP, and Kerberos private; support internal DNS access over VPN.
- [ ] Build browser-based Group Policy authoring for ADMX/ADML, Registry.pol, Group Policy Preferences, and baseline policies without RSAT/GPMC. Permit normal logon/startup scripts only; do not add remote WinRM/PowerShell command execution.
- [ ] Implement the standards-compliant identity-provider surface for OIDC/OAuth 2.0 and SAML 2.0, plus the AI.md-defined external OIDC/LDAP/SAML login and provider administration. Publish standards discovery/metadata and validate signing, key rollover, client registration, claims, group mapping, logout, session invalidation, and interoperability with multiple providers.
- [ ] Keep Samba authoritative for domain passwords, identities, and groups while identity federation handles web application SSO. Verify account disable/delete/group changes invalidate or reduce web access without stale credentials or parallel identity authority.
- [ ] Build separate browser workspaces for Server Administrators, Domain Administrators/delegates, and Domain Users. Server-admin routes use AI.md's `/server/{admin_path}` scope; domain-user pages use the Part 34 user scope; domain administration uses the authenticated user workspace under `/users/domains/{domain-id}`. Every page has its corresponding versioned JSON API using AI.md's route and response conventions.
- [ ] Create the Windows Server role/function parity matrix from Microsoft’s published role catalog, edition matrix, and migration catalog. Cover directory/federation/PKI, DNS/DHCP/IPAM/RADIUS, file/storage/DFS/NFS/iSCSI, print, web, remote access, remote desktop, virtualization, clustering, updates, backup/recovery, deployment, activation, and legacy roles. For each feature record user-facing behavior, standards/protocols, Linux/BSD implementation availability, client/version coverage, admin route/page, ports, dependencies, migration, backup/recovery, validation evidence, and any platform-specific difference. A missing equivalent is an unresolved release blocker for the complete parity claim; do not report feature parity based on a UI placeholder.
- [ ] Use the AI.md-approved admin route roots (`domains`, `roles`, `network`, `email`, `ssl`, `web`, `nodes`, `security`) for all project administration APIs/pages; keep each API versioned and pair it with its server-rendered admin page. Do not create custom first-level admin roots outside `valid_admin_root_paths()`.
- [ ] Cover every Windows Server-comparison role through Casad’s admin role catalog and role-specific web configuration, status, validation, diagnostics, lifecycle, and recovery screens. For kernel-bound or proprietary Windows behaviors, deliver and validate the corresponding Linux/BSD-native function; if no equivalent can be delivered, record it as an unresolved parity blocker rather than treating an unsupported label as completion.
- [ ] Server Admin workspace covers AI.md Part 17 setup/auth/admin account security, server and deployment health, all Windows Server-comparison roles, compatibility and install/upgrade status, domain/DNS/DHCP/time/mail/PKI/VPN/file/print/app configuration, public exposure, integrations, cluster/replication state, backup/restore, XDR/SIEM monitoring and incident controls, audit/logs, and global agent policy. Use AI.md's required admin route hierarchy without a `/config` grouping, with validation, confirmation, audit, server-rendered/no-JS-first, responsive, and accessible UI patterns.
- [ ] Domain administration uses authenticated user routes under `/users/domains/{domain-id}` with matching `/api/{api_version}/users/domains/{domain-id}` JSON routes. Authorization is separately derived from current domain groups and explicit delegated scope. Never expose domain administration publicly or rely on hidden UI controls for authorization. Server Admin routes remain under `/server/{admin_path}` and require Server Admin authentication.
- [ ] Domain-administration pages cover Samba users and groups, computers and machine accounts, OUs/delegations, DNS records and zones, GPO/ADMX content and links, domain health/replication, audit history, and managed-device assignments. Enforce Samba as the source of truth; show disabled/unavailable operations clearly where Samba lacks a supported API rather than implying they succeeded.
- [ ] The Server Admin web UI must expose every supported identity, domain, policy, network, application, integration, security, recovery, and service configuration capability. No supported infrastructure setting may be available only through CLI/TUI or an upstream vendor console. Define a route-to-screen-to-permission matrix from IDEA.md and ensure each product API is paired with its AI.md-compliant HTML workflow.
- [ ] Domain-user pages cover first-login projection of an active Samba identity, account identity and group-derived access, Keycloak/Samba-backed password change/reset, TOTP, passkeys/WebAuthn and recovery, own sessions/profile/preferences/notifications, user-scoped API-token lifecycle, assigned computers and read-only agent health, and VPN profile issue/revoke flows required by IDEA.md. Expose mailbox access through the integrated mail service without duplicating mailbox credentials or bypassing its authorization. User data stays private; public profile/discovery routes and user-owned agent enrollment/management are disabled.
- [ ] Keycloak policy for domain users must provide the AI.md Part 34 TOTP and passkey/WebAuthn capabilities and recovery, while Samba remains the password and domain-group authority. Verify password changes, disable/delete propagation, group changes, and expired/revoked sessions across Keycloak and Casad; never authenticate against a stale local password or keep access after the Samba identity is disabled.
- [ ] Map each screen and API operation to an explicit permission, target domain/object scope, and audit event. Domain Admin status must not imply Casad Server Admin or Linux host-root access; Server Admin status must not silently grant domain privileges; domain users see only their own data and explicitly public information.
- [ ] Validate against a fresh-domain baseline equivalent to Windows Server 2012 R2 and physical Windows 7+ Pro/Enterprise/Ultimate and Windows Server 2012+ member systems.
- [ ] Validate domain sign-in through each client OS's native authentication path, including Linux SSSD with NSS/PAM, supported BSD directory/PAM/NSS integration, macOS native directory/SSO, and Windows domain authentication. The Casad web CLI and telemetry agent do not authenticate domain users or replace those platform flows.

## 5. Casad Runtime Agent and Companion CLI

- [ ] Implement the required companion CLI with the AI.md Part 33 CLI/TUI and authentication behaviors. Keep it separate from the BSD/Linux server binaries.
- [ ] Make the Casad runtime agent a required product component and implement AI.md Part 33 naming, version parity, CLI/service commands, configuration precedence, setup, registration, health/status, updates, translations, logging, and native service integration on every AI.md-supported target.
- [ ] Use one Rust agent codebase for supported Linux, BSD, macOS, and Windows targets from the AI.md target matrix. Agents run directly on supported hosts using each platform's native service manager; keep the server binary Linux/BSD-only.
- [ ] Implement the full managed-host inventory contract: stable agent/device ID; hostname; OS edition/version/build and architecture; CPU/memory/storage/network summary; installed package/application inventory; local users, groups, and memberships without password hashes or secrets; service state; update state; certificate metadata without private keys; firewall posture; declared capabilities; health and last-check-in. Support bounded batches, timestamps, freshness, deletion/retention, and inventory access controls.
- [ ] Report a capability inventory that describes supported OS/version features and required local privileges without authorizing remote operations. Include inventory fields for services, updates, certificates, firewall posture, health, and local recovery capabilities; never report credentials or private keys.
- [ ] Linux adapter: collect supported host inventory, update/service state, certificate metadata, firewall posture, health, metrics, and security events using documented platform interfaces; apply only AI.md Part 33's bounded signed collector policy and never execute server-issued commands or host remediation.
- [ ] BSD adapter: define and verify inventory, security telemetry, metrics, and locally available capabilities by BSD release and privilege. Keep mobile-device management in configured third-party providers; do not ship Casad mobile binaries.
- [ ] macOS adapter: build the AI.md-supported agent and CLI targets; implement only validated, least-privilege telemetry collectors and report unsupported security/metrics sources explicitly. Native macOS directory login remains an OS platform flow.
- [ ] Windows adapter: build the AI.md-supported agent and CLI targets; implement only validated, least-privilege telemetry collectors and report unsupported security/metrics sources explicitly. Windows domain login remains a native Windows platform flow.
- [ ] Windows clients use native domain authentication protocols and Group Policy. Ship the AI.md-compliant Windows CLI and reporting agent; neither is an authentication provider or remote PowerShell/WinRM command runner.
- [ ] Keep agent reports bounded and schema-validated. The agent does not accept server-issued commands or task payloads; it reports only its own approved identity, health, inventory, and capabilities.
- [ ] Keep server-side policy authoring within supported native domain policy and Casad service configuration. Do not send desired-state changes to agents through routes outside AI.md Part 33.
- [ ] Protect reported inventory and agent credentials from disclosure or use outside the one registered agent scope; agent credentials cannot authorize host administration or server-issued operations.
- [ ] Agent-to-server flow: use AI.md Part 33 registration and agent-token lifecycle; send versioned heartbeats and bounded reports for the registered agent only. Keep communication outbound and require no inbound firewall openings.
- [ ] Windows domain enrollment and policy use supported native AD-compatible protocols. Do not put secrets in SYSVOL, Group Policy preferences, startup-script content, command arguments, history, or logs.
- [ ] Agent data flow: the server records and authorizes each registration, heartbeat, and report; agents report their own health and inventory and do not poll for or execute server-issued tasks.
- [ ] Use AI.md Part 33 agent routes under the Server Admin scope for registration, heartbeat, and reports. The report payload covers product-defined inventory, health, and capability data. Do not add machine task-polling or task-execution routes beyond AI.md's agent-token contract. Apply per-agent and domain authorization to all report data.
- [ ] Use AI.md's `/server/{admin_path}/agents/*` template routes for Server Admin agent management and machine registration, heartbeat, and reporting. Use `/users/domains/{domain-id}/agents` only for Domain Admin management and `/users/computers` for assigned-user read-only views; pair these user pages with versioned APIs. Do not add `/config`, `/domain/{domain-id}`, or root `/agents` route trees.
- [ ] Use the AI.md token prefixes and `agent` scope; do not introduce `adm_agt_` or `dom_agt_` credential types. Agent tokens may call only the AI.md registration, heartbeat, and report endpoints. Browser and machine credentials remain separated as specified by AI.md.
- [ ] Protect agent credentials with AI.md token handling, one-agent scope, immediate revocation, explicit rotation/re-enrollment, TLS validation, and safe offline reporting. Bound offline inventory buffering and report loss/overflow; no privileged work is queued for offline agents.
- [ ] Specify agent update provenance and recovery: signed release manifest and artifact checksum verification, supported-version policy, staged rollout controls, failure rollback, admin-visible version drift, and no update from an untrusted endpoint. Follow AI.md self-update requirements and ensure a compromised agent cannot issue updates to peers.

- [ ] Build the Server Admin agent console under AI.md's `/server/{admin_path}/agents` section: list/filter registered agents on all AI.md-supported platforms, inspect identity/OS/version/health/capabilities/last-seen/inventory, view report/audit history, revoke credentials, disable/re-enable agents, and show unsupported/stale/offline states. Never expose credential values after issuance.

Enforce delegated OU/group/device scope at query time and again before each report query or management view. ## 6. Availability, Backup, and Recovery

- [ ] Support one-host and role-based multi-host deployments, including same-LAN and cross-site layouts.
- [ ] Define the deployable service roles and dependency graph: Casad control plane; Samba AD DC/internal DNS; public BIND; Keycloak and its database; mail services and mailbox storage; PKI; VPN; shared application/backup storage; first-party event ingestion, detection/indexing, and host metrics storage. Preflight placement, platform compatibility, ports, DNS, storage, certificates, and resource requirements before installing or enabling any role. Build native BSD and Linux adapters for every supported host; represent unavailable per-release collectors and approved alternatives in the admin UI.
- [ ] Separate Casad app clustering from managed endpoint registration and from replication/failover of Samba, mail, DNS, and other service data.
- [ ] Implement service-specific replication, reconciliation, health checks, backup, and recovery. Do not create a generic all-state synchronization mechanism.
- [ ] Produce a service-state matrix before implementing multi-host promotion. For every role, name the authoritative writer, persistent state/config/secrets, replication mechanism, write consistency and lag limit, offline behavior, health signal, fencing dependency, backup/restore procedure, and promotion/failback steps. Cover Casad/SQLite-or-PostgreSQL, Samba directory data and SYSVOL, internal AD DNS, public BIND zones, Keycloak/PostgreSQL, mail queues and Dovecot mailbox state, CA keys/certificates, VPN state, SeaweedFS, and agent identity and report state.
- [ ] Use Samba's supported AD replication for domain controllers and verify SYSVOL replication separately; use Samba-integrated replication for internal AD DNS. Use authenticated and integrity-protected zone transfer for public BIND secondary zones. Do not infer that replication of LDAP/domain data also replicates SYSVOL or public DNS.
- [ ] Keep Keycloak nodes replaceable/stateless and persist Keycloak state in its dedicated PostgreSQL database; select and verify a PostgreSQL replication/fencing design before claiming Keycloak HA. Casad uses embedded SQLite for a single host and PostgreSQL for clustered/multi-host state per AI.md.
- [ ] For mail, define separate ownership and recovery for Postfix queues/configuration and Dovecot mailbox data; preserve acknowledged mail writes and prove mailbox consistency before promotion. If a safe replication method cannot be demonstrated, require manual recovery for mail rather than advertise automatic mail failover.
- [ ] For every service matrix row, disable automatic promotion when write consistency, replication freshness, or fencing cannot prove acknowledged-write safety. Expose the reason and the required manual recovery action in the Server Admin UI.
- [ ] For two-host full-stack promotion, require an outage longer than five minutes and quorum plus fencing or witness proof that the other host cannot write. If acknowledged-write safety is uncertain, do not promote.
- [ ] Permit deployments without automatic failover; require manual recovery when no safe witness/fencing mechanism is configured.
- [ ] Allow automatic failback only after the original host has been healthy and synchronized for 60 minutes. Support one-edge or dual-edge public exposure per deployment.
- [ ] Run encrypted remote full-stack backups nightly and before changes; retain 30 daily and 12 monthly copies by default. Verify backup integrity and perform restore checks for domain, mail, Keycloak, configuration, and compatible application data.
- [ ] Define backup units and consistent capture order for each stateful service, including Samba directory/SYSVOL, BIND zones, Keycloak/PostgreSQL, mail queues/mailboxes, PKI private keys, VPN credentials/configuration, Casad DB/configuration, SeaweedFS data, and agent trust/revocation state and bounded reports. Encrypt before remote transfer, keep encryption keys separate from backup storage, record version/restore dependencies, and never report success until verification passes.
- [ ] Provide a restore workflow that previews affected services, validates backup integrity and compatibility, requires explicit administrator confirmation, restores dependencies in order, prevents split-brain and restoration of stale agent credentials, and records a redacted audit trail. Test both full-stack and per-service restore without destroying the source backup.

## 7. Security, Admin, and Operations

- [ ] Separate host administration, Casad platform administration, domain administration, delegated helpdesk, and domain-user permissions.
- [ ] Implement and document the permission boundary matrix: host OS root/admin configures the Linux or BSD host and one-time privileged installation; Casad Server Admin manages Casad, integrations, server roles, backups, and global agent policy but is not automatically an AD Domain Admin; Domain Admin manages Samba domain objects and domain-scoped policy but is not a host administrator or Casad Server Admin; delegated helpdesk is limited to assigned objects/actions; Domain User manages only their own account/session, assigned device view, and permitted self-service services. Require an explicit grant for any cross-boundary action.
- [ ] Keep AI.md Server Admin accounts and domain-user identities separate. Server Admin authentication follows AI.md Part 17. Domain-user login follows IDEA.md's authoritative domain-identity requirement; bind external subjects to stable Samba identifiers and derive domain/delegated access from current authoritative membership. Remove or disable access promptly when the Samba account/group is disabled or removed.
- [ ] Record audit actor, auth method, source, target object, domain/OU/device scope, before/after values where safe, request/report ID, approval, result, and timestamp for privileged web/API/agent operations. Redact secrets, credential material, private keys, password hashes, and sensitive command output.
- [ ] Never store the host root password. Protect federation secrets, certificates, VPN credentials, mailbox contents, and backup encryption keys.
- [ ] Audit privileged changes to users/groups, DNS, GPO, federation, application catalog and app configuration, mail policies, security detections/incidents/response policies, service configuration, and recovery.
- [ ] Validate all published service ports and exposure combinations against IDEA.md: standard raw protocol ports, shared HTTP(S), client/egress-only dependencies, standard syslog connector ports, and private service-only paths. Casad agent telemetry uses outbound HTTPS to the server and adds no agent inbound listener. The admin UI must generate and validate the corresponding exposure/firewall policy per deployment.
- [ ] Apply service-scoped rate limits and bans first; propagate a global ban only for high-confidence cross-service abuse.
- [ ] Make public exposure configurable and never expose internal AD protocols globally.
- [ ] Use MIT for project-authored code and comply with AI.md dependency license and attribution rules.
